## Purpose

This runbook explains how to run and interpret the repository validation workflow.

`scripts/validate.mjs` is the single authority for validation task identity, canonical order, command arguments, and shard assignment. The default `npm run validate` still executes the complete inventory in canonical order. GitHub Actions discovers the required shard matrix from that same registry and executes every shard against one exact commit.

---

## Workflow

```text
.github/workflows/schema-validation.yml
```

Workflow name:

```text
Schema validation
```

Supported triggers:

```text
push to main
pull_request
```

### Exact-head parallel execution

The workflow has three required layers:

```text
discover
→ validation / <shard-id> matrix jobs
→ validate
```

- `discover` checks out and verifies `${{ github.event.pull_request.head.sha || github.sha }}`, verifies the canonical partition, and emits the dynamic shard matrix.
- Every `validation / <shard-id>` job checks out and verifies that same exact SHA, runs `npm ci`, and executes only its named canonical shard.
- Matrix `fail-fast` is disabled so all shard outcomes remain visible, but every shard is still required.
- The final job is named `validate`, runs with `if: always()`, and succeeds only when discovery and the complete shard matrix succeeded.
- A cancelled, skipped, missing, or failed shard is not a successful validation result.

---

## How To Run

For exact-head CI evidence, push a commit to an open PR branch or to `main`; the workflow starts from the corresponding GitHub event.

For local execution:

```bash
npm ci
npm run validate
```

Local execution proves the complete canonical plan ran in one process, but it does not replace the required exact-head parallel GitHub Actions evidence.

## What A Pass Means

A successful `Schema validation / validate` result means:

```text
- discovery verified the exact tested commit;
- the canonical task partition was complete and non-duplicated;
- every required shard checked out the same exact commit;
- every canonical validation task executed exactly once in the full CI plan;
- every required shard succeeded;
- the final validate aggregate succeeded.
```

A successful individual shard is only partial evidence. It does not imply complete repository validation.

---

## What A Pass Does Not Mean

A passing workflow does not prove:

```text
- real Elementor UI controls exist;
- live Elementor render matches the screenshot;
- responsive behavior is correct;
- SVG/assets are safe and final;
- real Elementor export JSON / EDIS is valid;
- exact pixel matching is achieved;
- production readiness;
- fresh independent PR Inspector review passed;
- merge, approval, or deployment occurred.
```

## Failure Triage

### Discovery fails

Likely causes:

```text
exact checked-out SHA mismatch
invalid canonical registry
missing, duplicated, empty, or unknown shard/task assignment
invalid dynamic matrix output
```

Run locally:

```bash
node scripts/validate.mjs --verify-partition
node scripts/validate.mjs --list-shards
node scripts/validate.mjs --plan
node scripts/test-validation-sharding.mjs
```

### A validation shard fails

The failing job name identifies the shard. Expensive Runtime tests and the former tail commands are independently bounded so the failing job maps directly to one high-cost or diagnostic-sensitive command. The runner also logs the exact canonical command label before execution.

Run only that shard locally:

```bash
node scripts/validate.mjs --shard <shard-id>
```

Do not delete, skip, make optional, or move the failing task to scheduled-only execution.

### Final `validate` fails

The final aggregate fails when discovery or any required matrix shard did not succeed. Inspect `discovery_result` and `validation_shards_result`, then open the corresponding discovery or shard job.

A cancelled or skipped matrix member is incomplete evidence and must not be reported as success.

### Valid package fails

Likely causes:

```text
schema changed but valid fixture was not updated
example package missing a newly required field
JSON syntax error
```

Fix the relevant fixture or package only when repository authority supports that change.

### Invalid fixture passes unexpectedly

Likely causes:

```text
schema is too permissive
invalid fixture no longer violates the schema
```

Do not weaken an existing assertion merely to obtain a green shard.

### Cross-field validator fails valid package

Likely causes:

```text
missing class map entry
unknown target_element
unknown child node reference
generation/source mismatch
```

### Checkpoint fixture fails

Likely causes:

```text
checkpoint.schema.json changed
fixture is stale
```


`npm run validate` remains the complete local interface. Shard execution is a bounded diagnostic and CI orchestration interface, not a reduced replacement for full validation.

---

## Release Rule

Do not treat the repo or PR as merge-ready until:

```text
- Schema validation / validate passes on the exact resulting PR Head;
- no required shard is missing, cancelled, skipped, or failed;
- a fresh PR Inspector review is bound to that exact Head;
- any additional repository-specific owner checks are complete.
```
